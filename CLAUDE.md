# air-pollution-tracker

Java 17 multi-module Maven project: air pollution microservices.

## Modules

- `pollution-common` — shared utilities; every service depends on it. Among them the health server every application runs for a container platform's probes (`com.pollution.common.health`, see *Running in containers*).
- `persistence-common` — the shared persistence abstractions only: the cache (`IPollutionCache<T>`), the repository interfaces over the relational store (`IPollutionRepository`, with the records its aggregate queries return in `com.pollution.persistence.entities`), the stores shared between services (`ILatestReadingStore` with its cache-backed implementation) and, in `config/Config`, the settings of those shared stores; depends on `pollution-common` and on **no backend driver**. Every service that keeps state depends on it.
- `persistence-redis` — the Redis implementation of the cache (`RedisPollutionCache<T>`) plus jedis; depends on `persistence-common`. Only services that use the cache (collector, writer, analyzer, alert service, API service) depend on it.
- `persistence-postgres` — the PostgreSQL implementation of the repository interfaces, through Hibernate ORM, and the one place that knows the table layout; depends on `persistence-common`. Only services that read or write the relational store (writer, API service) depend on it.
- Persistence modules are split so that no service transitively pulls a driver it does not use: a Redis-only service never sees the Postgres driver and vice versa. A new backend gets its own `persistence-<backend>` module; its abstractions go in `persistence-common`.
- `pollution-data-collector` — service that collects pollution data and publishes it. `PURPLEAIR_SENSORS` lists every sensor, the same on every instance: the running instances find each other through Redis (a lease per instance, renewed by heartbeat) and share the sensors out by rank, so a collector can be started or stopped at any time and the others reshare within a heartbeat or so (see the collector's `membership/` layer and *Running in containers*).
- `pollution-data-writer` — service that stores pollution data: readings go to PostgreSQL through `IPollutionRepository` (the history) and to Redis through `ILatestReadingStore` (each series' current reading, for fast "right now" lookups by the API service); averages are consumed but only logged so far.
- `pollution-data-analyzer` — service that analyzes pollution data.
- `pollution-alert-service` — service that detects threshold exceedances in readings and rolling averages, delivers each `PollutionAlert` to people over a channel (Telegram, …). Publishes no topic: the alert service's own INFO log is the record of every alert.
- `pollution-api-service` — service that serves the dashboard over HTTP: its pages (vanilla JS modules + CSS, Chart.js vendored under `static/vendor/`, no build step) — the overview at `/`, one source's history at `/history` — and the read-only JSON API under `/api/` that they draw from — every source's current reading from Redis through `ILatestReadingStore`, its history and Postgres-side aggregates through `IPollutionRepository`. Consumes no Kafka topic.

## Configuration rules

- Every microservice module MUST have a `config` folder — the package `com.pollution.<service>.config` — containing two classes:
  - `Config.java` — values only: all of a service's settings (service name, endpoints, paths, tuning values) as constants or static accessors. The rest of the service reads configuration only through `Config`.
  - `Wiring.java` — object assembly only: the `create...()` factories that build the service's object graph from `Config` values. This is the one place per service that names concrete implementations; everything it returns is typed as an interface, and `main` calls `Wiring`, never constructors.
- Environment variables are read only through `com.pollution.common.config.Env` (`Env.getLong("NAME", default)` etc.), and only from a `Config` class. No `System.getenv(...)` / `System.getProperty(...)` anywhere else. Each service declares its own variable names and defaults — `Env` is the mechanism, not a shared value store. A variable that is not set in the process environment is taken from the nearest `.env` file (the working directory's, else the closest parent's — so the repository root's is found from any module): `NAME=value` lines, `#` comments, empty value = unset; the process environment always wins. `.env` is git-ignored and holds local secrets such as the Telegram bot token; `.env.example` (committed) lists what goes in it. The one variable not read through `Env` is `LOG_FORMAT`, which logback reads itself (see the logging rules).
- Services do not read `Config` from business classes; `Wiring` passes settings in through constructors (e.g. the collector's poll interval), so classes stay testable without environment setup.

## Messaging rules

- Services talk to each other only through the `IPublisher<T>`/`ISubscriber<T>` interfaces from `com.pollution.common.pubsub`. A service must never know it is talking to Kafka: no `org.apache.kafka.*` or `com.pollution.common.pubsub.kafka.*` imports anywhere in a service module's business code.
- The concrete implementation (`KafkaPublisher`/`KafkaSubscriber`) is named and instantiated in exactly one place per service — its `config/Wiring.java` — and handed to the rest of the service as the interface type.

## Persistence rules

- Services keep durable state only through the `IPollutionCache<T>` interface from `com.pollution.persistence` (`persistence-common`): a typed object cache over string keys — get, set (with an overload taking a `Duration` TTL, after which the store drops the key on its own), remove, and lookups by key pattern — with values stored as JSON via `JsonSupport`. A service must never know it is talking to Redis: no `redis.clients.*` or `com.pollution.persistence.redis.*` imports anywhere in a service module's business code — and likewise never that it is talking to PostgreSQL or Hibernate: no `org.postgresql.*`, `java.sql.*`, `jakarta.persistence.*`, `org.hibernate.*` or `com.pollution.persistence.postgres.*`.
- Keys are global to the store, so each service owns a key **prefix** constant in its own `Config` (`<service>:<concept>:`, e.g. `analyzer:rolling-average-state:`, `alert:last-sent:`, `collector:member:`), only ever reads and writes keys under it, and finds its objects with the pattern `<prefix>*`. State that is shared between services is the exception: its prefix is owned by a shared store in `persistence-common` (`latest-reading:` — no service name, since no service owns it) and services only touch those keys through that store.
- The concrete implementation (`RedisPollutionCache<T>` from `persistence-redis`, one instance per value type, built with the `Class<T>`) is named and instantiated only in a service's `config/Wiring.java`. Redis connection settings (`REDIS_HOST`/`REDIS_PORT`) live in `com.pollution.persistence.redis.config.Config` (in `persistence-redis`); each backend module keeps its own `config/Config` for its connection settings.
- A service wraps the cache behind a domain-specific store interface in its `persistence/` package (e.g. the analyzer's `IRollingAverageStateStore`), so business code speaks in domain terms (save this sensor's state) rather than keys and values. A store that several services share goes in `persistence-common` instead, next to `IPollutionRepository`, so they all use the same class and cannot disagree about the keys.
- Each series' current reading — the newest `PollutionData` of one source and pollutant — is kept through the `ILatestReadingStore` interface from `com.pollution.persistence` (`persistence-common`), which throws the unchecked `PollutionCacheException`. Its contract: `save` never moves a series backwards (it returns `false` when a newer reading is already stored, so a redelivered old message is harmless), `find` gives one series' current reading, `findAll` every series' — the "right now" view the API service shows. The implementation, also in `persistence-common`, is `CacheBackedLatestReadingStore` over an `IPollutionCache<PollutionData>` (any backend; the writer's and the API service's `Wiring` give it a `RedisPollutionCache`): one key per series, `latest-reading:<source>:<POLLUTANT>`, stored with a TTL (`com.pollution.persistence.config.Config.getLatestReadingTtl()`: `LATEST_READING_TTL_MINUTES`, default 60) so a sensor that stops reporting drops out of the current view instead of showing a stale value forever. The TTL is declared in `persistence-common`, not in a service, because it is part of the shared store's contract like its key prefix, and every service that builds the store needs the same value. There is no stand-in: the writer and the API service need Redis.
- Readings are kept long-term through the `IPollutionRepository` interface from `com.pollution.persistence` (`persistence-common`), which throws the unchecked `PollutionRepositoryException`. Its contract: `save` is idempotent (`true` if the reading was stored now, `false` if one with the same source, pollutant and timestamp was already there); `findReadings` gives one series', or one source's every pollutant's, readings oldest first; the aggregates the dashboard's history is built on are computed by the database rather than in a service — `findSources()` (every source with readings, as `SourceSummary`), `summarize(source, from, to)` (one `ReadingsSummary` per pollutant with readings in the range) and `findAverages(source, from, to, bucket)` (one `BucketAverage` per pollutant per epoch-aligned bucket that has readings; a native epoch grouping, so it works for any bucket length); every range is `[from, to)`. Being already domain-specific, it is used directly by business code, without a per-service wrapper. The implementation is `PostgresPollutionRepository` in `persistence-postgres` (Hibernate ORM over PostgreSQL; owns the `SessionFactory`/HikariCP pool, `close()` releases it), named only in a service's `config/Wiring.java`. Connection settings (`POSTGRES_HOST`/`PORT`/`DB`/`USER`/`PASSWORD`/`POOL_SIZE`) live in `com.pollution.persistence.postgres.config.Config`.
- JPA-annotated classes are **not** domain entities: they are the mutable row forms Hibernate needs, live only in `persistence-postgres` (`com.pollution.persistence.postgres.entities`, e.g. `PollutionDataEntity` for table `pollution_data`), and never leave that module — a domain object goes in through `fromDomain(...)` and comes out through `toDomain()`. Enums are stored as their names through an `AttributeConverter` (`PollutantConverter`), not `@Enumerated`, so no check constraint freezes the set of values. The schema is created/updated by Hibernate at startup (`hibernate.hbm2ddl.auto=update`); `pollution_data` has a unique constraint on `(source, pollutant, measured_at)`, and a save that hits it returns `false` instead of failing (Hibernate's own logging of that SQL error is switched off in the shared `logback.xml`; a real failure still reaches the caller as `PollutionRepositoryException` with the SQL details). Ids are sequence-generated so inserts can be batched.

## Threshold rules

- The concentrations above which a measurement is an exceedance are one shared value, `com.pollution.common.thresholds.Thresholds` in `pollution-common`: a validated record of a baseline per `Pollutant` in its unit (WHO 2021 24-hour guideline levels, except PM2.5 at 25 µg/m³ — WHO interim target 4), a factor per rolling-average window (`windowFactors`: 24 h ×1, 1 h ×1.25, 10 min ×1.35) and the `readingFactor` of a single reading (×2); `readingThreshold(pollutant)` and `windowThreshold(pollutant, window)` do the multiplying. `ThresholdsLoader` reads them from **`pollution-common/src/main/resources/thresholds.json`** — the file's shape is the record's — which is packaged with every service and is the one source of truth: change it and rebuild, and every service changes at once. The only setting is `THRESHOLDS_FILE` (`com.pollution.common.config.Config.getThresholdsFile()`), naming another file to read instead, for tuning without a rebuild; there are no per-value env overrides. A service that judges a value against a threshold — the alert service to raise alerts, the API service to tell the dashboard what to mark — gets the `Thresholds` through its own `Config.getThresholds()` and keeps no threshold of its own, so they cannot disagree.

## Package layout rules

- Entities — the data types the system is about (messages, readings, sensors, enums of domain values) — live in an `entities` package: `com.pollution.common.entities` for types shared across services (`AbstractMessage`, `Pollutant`, `PollutionData`, `PollutionAverage` with its per-window `WindowAverage`, `PollutionAlert`, `SourceId`) and `com.pollution.<service>.entities` for service-specific ones. A source — `PollutionData.source`, the key every store files a series under — is one string, `<provider>:<sensor>` (`purpleair:Ganei-Ayalon`); `SourceId(provider, sensor)` is the one place that spells that form out (`parse`, `tryParse` — empty for a string that is not one — and `toString` back to the string): the collector builds ids with it, the API service takes them apart with it, and nothing else splits on `:`. Entities are immutable value types (records/enums, or final classes with final fields and value `equals`/`hashCode`) with no I/O and no dependencies on APIs, Kafka, or config — no Jackson annotations either. Messages extend the abstract class `AbstractMessage` (which holds `city` and `timestamp`) and expose exactly one public constructor whose parameter names match the field names: that is how `JsonSupport` in `pollution-common` rebuilds them from JSON (the build keeps parameter names via `javac -parameters`).
- Services are organized **by layer, then by provider**. Each layer is a top-level package holding only provider-agnostic types (interfaces, shared helpers); everything specific to a data provider goes in a sub-package named after it (`<layer>/purpleair`). The collector's layers:
  - `entities/` — `Shard(rank, count)`: one instance's share of what the group shares out — `select(list)` gives the items at positions `rank, rank + count, …`, so the shares of a group cover a list exactly once and differ in size by at most one; `Shard.NONE` is the share of an instance not in the group, nothing. `Member(id, since)`: one instance as the group knows it. `entities/purpleair/` holds `PurpleAirSensor` (PurpleAir's `sensorIndex` and our `city` — PurpleAir exposes none. A value, not an enum, because which sensors exist is configuration: the record owns its textual form, `<sensorIndex>=<city>` as in `308702=Ganei Ayalon`, through `parse` and `toString`, like `SourceId`), `PurpleAirReading`, `PurpleAirSensorInfo`. The sensors come from `Config.getSensors()`: `PURPLEAIR_SENSORS`, a comma-separated list in that form, over a compiled default list; a malformed entry fails at startup. Every instance gets the whole list; which of them it polls is its `Shard`, worked out by the membership, never configured.
  - `api/` — access to external APIs: `IApiKeyProvider`, `RoundRobinApiKeyProvider`; `api/purpleair/` holds `IPurpleAirSensorApi` (PurpleAir's per-sensor endpoint as the registry and the fetcher see it), `PurpleAirSensorApi` (its HTTP implementation, the only class that talks to PurpleAir; the tests hand the registry and fetcher a fake) and `PurpleAirApiException`. The read keys are `Config.getPurpleAirApiKeys()`: `PURPLEAIR_API_KEYS`, comma-separated, **required** — a secret, so no default is compiled in (the repository is public); it comes from `.env` locally and from a Kubernetes `Secret` in a cluster, and a collector without one fails at startup.
  - `registry/` — which sensors we follow and their metadata: `ISensorRegistry<S, I>` (`sensors()` — the followed ones, empty until `follow(Shard)` — `enrichSensor`, `get`); `registry/purpleair/PurpleAirSensorRegistry` is given every configured sensor (rejects an empty list or a sensor index listed twice) and follows nothing until told a shard; `follow` enriches the sensors gained (a failure is logged and the sensor followed un-enriched; metadata is kept for a sensor no longer followed, so regaining it costs no request) and logs every change of share with what was gained and dropped, so an instance's log says what it owns at any time.
  - `fetchers/` — turning provider data into `PollutionData`: `IReadingsFetcher` (`follow(Shard)`, `sources()` — the followed sensors' sources as `fetch()` would name them now, no I/O — `fetch()`); `fetchers/purpleair/PurpleAirReadingsFetcher` hands the shard to the registry; its sources are `SourceId`s of provider `purpleair`, named after the sensor's PurpleAir name — or its sensor index while enrichment keeps failing, retried on every fetch.
  - `persistence/` — where the group registers: `IMembershipStore` (`renew(Member, lease)`, `members()`, `leave(Member)`, `close()`; throws `PollutionCacheException`); `CacheBackedMembershipStore` keeps one object per instance in an `IPollutionCache<Member>` under `Config.MEMBER_KEY_PREFIX + id` (`collector:member:<id>`) with a TTL of the lease, so an instance is a member exactly while its key exists, and lists the group with `<prefix>*`.
  - `membership/` — this instance's place in the group: `IGroupMembership` (`start(IShardListener)`, `close()` — leaves the group), `IShardListener` (`shardChanged(Shard)`, called on the membership's thread), `LeaseGroupMembership`: every heartbeat (`Config.getHeartbeatInterval()`: `COLLECTOR_HEARTBEAT_MS`, default 10 s) it renews its lease (`Config.getLease()`: `COLLECTOR_LEASE_MS`, default 30 s; at least two heartbeats, checked, so one failed heartbeat never ends it) as `Member(Config.getCollectorId(), …)` — `COLLECTOR_ID`, default `<hostname>-<pid>`: unique on a machine, and the same again when a container restarts, so the restarted instance replaces its old registration instead of standing beside it until the lease runs out — lists the members, ranks them by id and takes the `Shard` of its rank, telling the listener when it changed. No coordination: every instance sees the same registrations and ranks them the same way. *Joining*: the first heartbeat only registers; the shard comes with the second, by when every other member has had a heartbeat, seen the newcomer and let go of its sensors — a join never makes two instances poll one sensor. *Leaving*: `close()` removes the registration and the others take over at their next heartbeat; an instance that dies lapses when its lease runs out — that long plus a heartbeat, its sensors go unpolled. *Losing the lease*: heartbeats failing, the instance keeps its shard while its last renewal is younger than the lease (the others still see it) and drops everything (`Shard.NONE`) once it is older, because the others have taken its sensors by then — better a short gap than two collectors on one sensor — and rejoins as a newcomer when the store answers again. A listing that fails keeps the current shard; a listener that throws is logged and the heartbeats go on.
- Layers depend downward only: `fetchers → registry → api → entities` and `membership → persistence → entities`; `PollutionDataCollectorService → membership, fetchers`. A shard the membership hands the service is applied on the poll thread (`IReadingsFetcher.follow`, then the cached readings of sources no longer in `sources()` are dropped so they stop being republished, then the sensors gained are polled at once rather than at the next scheduled poll); an instance whose shard holds no sensor polls and warns about nothing. `close()` leaves the group before stopping the loops. A layer's top-level package never imports from a provider sub-package, and a provider sub-package never imports from a *sibling layer's* provider sub-package except along that same direction. Provider-agnostic interfaces must not mention provider types — generify them (as `ISensorRegistry<S, I>`) rather than leak `PurpleAir*` into a top-level package.
- If a class would work unchanged for another provider, it does not belong in a provider sub-package.
- The analyzer's layers:
  - `entities/` — `Reading`, `SensorPollutant` (the identity of a series: one sensor's readings of one pollutant), `RollingAverageState`.
  - `analysis/` — `RollingAverage`: one rolling window of one series; produces and restores from `RollingAverageState`. A reading not newer than the series' newest one is ignored: a series' readings arrive in timestamp order (the collector steps every republish forward, the messaging keeps a series on one partition), so such a reading is a repeat — a redelivery after a crash, or a collector that restarted or re-polled an unchanged sensor and emits the same timestamps again — and is counted once, just as the writer's repository stores it once. Restoring replays the persisted readings without that check. `RollingAverageGroup`: all of a series' windows (default 10 min, 60 min, 24 h — `Config.getRollingAverageWindows()`, one `RollingAverage` each, ascending), fed the same readings; hands out the longest window's state for persistence and the `List<WindowAverage>` for publishing.
  - `persistence/` — durable per-series state storage: `IRollingAverageStateStore`; `CacheBackedRollingAverageStateStore` keeps one object per series in an `IPollutionCache<RollingAverageState>` under `Config.ROLLING_AVERAGE_STATE_KEY_PREFIX + sensorId + ":" + pollutant` (provider-agnostic — the concrete cache is chosen in `Wiring`); `LoggingRollingAverageStateStore` is a no-persistence stand-in for running without a cache.
  - Direction: `PollutionDataAnalyzerService → persistence, analysis → entities`.
  - Persistence model: only a series' **longest** window is persisted, saved (overwriting the previous state) after every reading that changes the series. On startup every series is loaded once and each shorter window is rebuilt from the longest one's state by replaying its readings through `RollingAverage.loadFromPersistence`, which drops those outside the shorter window. There is no periodic flush. Every save stores the state with a TTL (`Config.getRollingAverageStateTtl()`: `ROLLING_AVERAGE_STATE_TTL_MINUTES`, default the longest window — after that long without a save every stored reading is outside the window anyway), so a series that stops being updated expires from the cache instead of lingering forever.
  - Publishing: after every reading that changes a series, one `PollutionAverage` (city, source, pollutant, one `WindowAverage` per window, timestamp = the newest reading) goes to `POLLUTION_AVERAGE_TOPIC`, keyed by source.
- The writer's layers (package `com.pollution.datawriter`):
  - `PollutionDataWriterService` owns the two subscribers (`POLLUTION_DATA_TOPIC`, `POLLUTION_AVERAGE_TOPIC`), the `IPollutionRepository` and the `ILatestReadingStore`; every reading is saved to the repository and then made the series' current reading in the store — the two writes are independent, each failure logged, not propagated (the repository is idempotent, so a redelivery stores it; the store never goes backwards) — averages are only logged for now. `DataWriterApplication` wires and starts it, exactly like the analyzer's application.
  - Direction: `PollutionDataWriterService → IPollutionRepository, ILatestReadingStore`.
- The API service's layers (package `com.pollution.apiservice`):
  - `entities/` — what the API answers with: `PollutantInfo` (name, display name, unit and `thresholds` — the effective threshold per measurement length, `raw` for a single reading and one per rolling-average window keyed by its ISO length, `PT10M`/`PT1H`/`PT24H`, worked out from the shared `Thresholds` — so the page needs no copy of `Pollutant` and never multiplies a factor itself), `SourceStatus` (a source — its whole id, the key the stores and `/api/history` know it by, and its `provider` and `sensor` taken apart with `SourceId.tryParse`, `provider` being `null` for an id that is not a `SourceId`, so the page never splits ids itself — its city, when it last reported at all, and its current reading per pollutant — empty when it stopped reporting), `HistoryPoint` (one pollutant at one time or over one bucket: time, mean, min, max, count — a single reading is a bucket of one, so the page draws readings and averages the same way) and `SourceHistory` (source, range, bucket or `null` for raw readings, the range's `ReadingsSummary` per pollutant, the points oldest first).
  - `queries/` — the logic, with no HTTP in it: `SourceOverviewQuery` joins `IPollutionRepository.findSources()` with `ILatestReadingStore.findAll()` into `SourceStatus`es (a source known to only one store is listed anyway; a store that fails makes the whole query fail — a view missing one store would be wrong, not incomplete). `HistoryQuery` builds a `SourceHistory`: fills in the range (`to` defaults to now, `from` to `to` minus `Config.getDefaultHistoryRange()`: `API_DEFAULT_HISTORY_HOURS`, default 24), refuses one longer than `Config.getMaxHistoryRange()` (`API_MAX_HISTORY_DAYS`, default 365), takes raw readings when no bucket is given and `findAverages` otherwise, and always adds `summarize`.
  - `web/` — the HTTP layer, provider-agnostic: the `Request` and `Response` records (a response carries its cache policy: `json`/`bytes`/`error` — the latter `{"error": …}` — are all `no-cache`, `longLived(...)` is for content that only changes by changing name), `IRequestHandler` (`Response handle(Request)`), `IWebServer` (`start()`, `close()`), and `Router` — the one `IRequestHandler` the server sees: exact path → handler, everything else → the fallback, only `GET` (405 otherwise), and the error mapping: `IllegalArgumentException` → 400 (a bad parameter — handlers and queries throw it for bad input), `PollutionRepositoryException`/`PollutionCacheException` → 503, anything else → 500, logged — and one INFO access line per answered request, whatever the outcome: method, path, status and duration. Handlers: `SourcesHandler` (`GET /api/sources` → `[SourceStatus]`), `HistoryHandler` (`GET /api/history?source=…&from=<ISO instant>&to=<ISO instant>&bucket=raw|<ISO duration such as PT10M, PT1H, P1D>` → `SourceHistory`; only `source` is required), `PollutantsHandler` (`GET /api/pollutants` → `[PollutantInfo]`, built once from `Config.getThresholds()`), `LimitsHandler` (`GET /api/limits` → `HistoryLimits`, the default and maximum history range — told to the page so it validates before asking; the service still enforces them), `StaticResourceHandler` (the pages by the path they are opened at — `/` → `static/index.html`, `/history` → `static/history.html` — and any other path → the file of that name under the classpath directory; only plain file names of known types, so nothing outside it can be reached). Here the "provider" is the HTTP server: `web/jdk/JdkWebServer` is the only class that imports `com.sun.net.httpserver` (the JDK's own server, module `jdk.httpserver` — no dependency); it turns each exchange into a `Request`, hands it to the handler and writes the `Response` with its cache policy (`no-cache` everywhere except the pinned libraries under `static/vendor/`, which `StaticResourceHandler` serves long-lived and `immutable` — upgrading one means renaming the file), on a fixed pool of `Config.SERVER_THREADS` threads. Its address is `Config`: `API_BIND_ADDRESS` (default `127.0.0.1` — the dashboard is reachable only from the machine unless set to `0.0.0.0`) and `API_PORT` (default 8080).
  - Direction: `web/jdk → web → queries → entities`; `queries → IPollutionRepository, ILatestReadingStore`. No business code sees the HTTP server, Redis or Postgres; `Wiring` names them all and builds the `Router`.
  - The pages (`src/main/resources/static/`) are dark blue, and only that: `theme.css` holds every colour, radius and font as custom properties on `:root` (ground/surface layers, text hierarchy, one accent blue for interactive elements, states — among them `--exceed`, the one warm colour, for a value above its threshold — one colour per pollutant, `color-scheme: dark` so native controls follow) and is the only file that declares a colour; `style.css` holds the components of both pages and reads tokens only; the charts pull their colours through `getComputedStyle`, so a theme change needs no JS. The scripts are ES modules: `common.js` (the helpers shared by both pages — the `api()` fetch, the pollutant catalogue, `historyUrl()` and `sourceCard()`, the card of one `SourceStatus`, one component for both pages), and one per page, `overview.js` and `history.js`; Chart.js is loaded by the history page only.
  - `index.html` (`/`, `overview.js`): a responsive card grid, one card per source, refreshed every 60 s from `/api/sources` (the pages poll on their own; there is no refresh button or status). A card is an `<a>` to `/history?source=…` showing the labelled `sensor`, `provider` and `city` — the sensor on top — one tile per current reading (value and unit, in the pollutant's colour — a pollutant keeps one colour everywhere; a value above the 1-hour threshold (`PT1H` in `/api/pollutants` — deliberately not the single-reading one, which is for alerting on spikes) shows the value and the tile edge in `--exceed` with that threshold in its tooltip, and nothing else on the card changes) or "no current reading" for a source that stopped, and "updated / last reported x min ago" (absolute on hover), with a `History` cue that fades in when the card is hovered or keyboard-focused (always shown where there is no hover — touch screens). A refresh that returns unchanged data leaves the DOM alone — only the relative texts are rewritten in place.
  - `history.html` (`/history?source=…`, `history.js`): the source's card (the same component, not a link, refreshed every 60 s; `document.title` becomes the sensor), then range presets (24 h default, 48 h, 7 d, 30 d, 1 year — always ending now), a custom range as two day pickers (whole local days, end day inclusive, prefilled from the shown range, applied on change — no Apply button — and validated against `/api/limits` before asking); the averaging is not a control but follows the range's length — 10-minute buckets up to 2 days, hourly up to a month, daily beyond, so a chart has 144–720 points whatever the range — and the status line says which; then one Chart.js line chart per pollutant (the mean with a min–max band and, dashed in `--exceed`, the threshold of averages of the bucket length — the `PT10M`/`PT1H`/`PT24H` threshold of `/api/pollutants`; means above it are marked in `--exceed` and the tooltip says so) with the range's summary line above it — or, when the range has no readings, one empty chart spanning it, so there is always a graph. The controls' state is kept in the URL (`range` and `from`/`to` for custom days) through `history.replaceState`, so a view is shareable and reloads as it was while Back still returns to the overview; whatever is missing or unusable in the URL gets its default. Without `source` the page shows an error and the link back.
  - Both pages: times are shown in the browser's zone but formatted in English whatever its language (`LOCALE = 'en-GB'` in `common.js`: day before month, 24-hour clock — the one place a locale is named); text goes into the DOM with `textContent`, never `innerHTML`; a response that is no longer the latest request's is never rendered (each fetch carries a request number).
- The alert service's layers (package `com.pollution.alertservice`):
  - `entities/` — `AlertSeries` (the identity of an alert series: source, pollutant and window, `null` window for single readings; alerts in one series share a cooldown).
  - `detection/` — `ThresholdDetector`: judges by the shared `Thresholds` (`Config.getThresholds()`; see the threshold rules) — a baseline per `Pollutant` times the factor of the measurement type, the shorter the measurement the more it swings; a window with no factor uses ×1 and is warned about once. Applied to raw `PollutionData` values and to every `WindowAverage` of a `PollutionAverage`; strictly above → one `PollutionAlert` per exceeding measurement, carrying the measurement's timestamp, the effective threshold and, for averages, its window.
  - `persistence/` — the cooldown: `IAlertCooldownStore` (`coolingDownSeries(source, pollutant)` — every series of that source and pollutant marked sent less than its cooldown ago; `markSent(PollutionAlert)`). `AlertCooldowns` says how long each kind of series stays quiet: a window's average uses the window's own length unless overridden, a single reading its own value (`Config.getWindowCooldowns(windows)` — for the windows the `Thresholds` have factors for — / `getReadingCooldown()`: `ALERT_COOLDOWN_MINUTES_PT10M` / `_PT1H` / `_PT24H` / `_RAW`, defaults 10 / 60 / 1440 / 10; `ALERT_COOLDOWN_MINUTES` alone overrides all four, for testing). `CacheBackedAlertCooldownStore` stores the last alert of a series in an `IPollutionCache<PollutionAlert>` under `Config.LAST_SENT_KEY_PREFIX + source + ":" + pollutant + ":" + (window ISO string, or "raw")` — e.g. `alert:last-sent:12345:PM2_5:PT24H` — with a TTL of that series' cooldown, so a series is cooling down exactly while its key exists, and finds a source's series with the pattern `<prefix><source>:<POLLUTANT>:*` (glob characters in the source escaped); `InMemoryAlertCooldownStore` is the stand-in for running without a cache.
  - `senders/` — delivering a `PollutionAlert` to people over one channel: `IAlertSender` (`send(PollutionAlert)`, throwing the unchecked `AlertSendException` when delivery fails; `close()` releases the channel's resources). Here the "provider" is the delivery channel: each implementation lives in `senders/<channel>/`. `senders/telegram/TelegramAlertSender` posts each alert to one dedicated Telegram **channel** (the bot must be a channel admin with "post messages") through the Bot API's `sendMessage` (JDK `HttpClient`, one POST per alert, plain text with no `parse_mode`); it takes the `PollutionAlert` entity and renders it to words only there, at the edge — nothing upstream formats messages. The message names the pollutant, the sensor's city, the cause (single reading or which average), the value and the threshold; the source id is not named — the city places the alert. Its settings (`Config`): `TELEGRAM_BOT_TOKEN` (from BotFather), `TELEGRAM_CHAT_ID` (the channel's `-100…` id, or `@username` for a public channel), `TELEGRAM_API_BASE_URL` (default `https://api.telegram.org`), `TELEGRAM_TIMEOUT_SECONDS` (default 10). The token is part of the request URL, so the sender never logs the URL or puts it in an exception. `LoggingAlertSender` (top-level, channel-agnostic) is a no-delivery stand-in that only logs, for running without a real channel. `Wiring.createAlertSender()` returns the Telegram sender when `Config.isTelegramConfigured()` (token **and** chat id set; setting only one fails at startup), else the logging stand-in.
  - Direction: `PollutionAlertService → detection, persistence, senders → entities`.
  - Flow: `PollutionAlertService` subscribes to `POLLUTION_DATA_TOPIC` and `POLLUTION_AVERAGE_TOPIC` (two subscriber threads, one lock around raising). A message's alerts are raised **longest window first** (`PollutionAlertService.LONGEST_WINDOW_FIRST`), so when several windows of one `PollutionAverage` exceed at once only the longest is sent and the shorter ones are dropped as superseded — one post, not one per window, at the first crossing and again each time the longest one's cooldown lapses. For every alert the detector finds: if its series is cooling down, drop it; if a **longer** measurement of the same source and pollutant is cooling down (`AlertSeries.supersedes`: any window supersedes a single reading, a longer window a shorter one — a spike is old news while the hour is already alerting), drop it too; otherwise send it through the `IAlertSender` (a failure is logged, not retried), then mark the series sent regardless of the outcome — the inputs repeat every few seconds, so a broken channel must not be retried at that rate — and log the raised alert at INFO, so the service's log is a record of every alert whatever the channel. A cooldown store that cannot be read counts as not cooling down (duplicates over missed alerts).
  - `PollutionAlert.window` is `null` for an alert raised by a single reading and the rolling-average window otherwise.
- Every entity gets its own `.java` file — never nest one entity record inside another.
- JSON outside Kafka (persistence, rolling-average state) goes through `com.pollution.common.json.JsonSupport` (`toJson`/`fromJson`, throwing the unchecked `JsonException`). It holds the single shared Jackson configuration; the Kafka serializers use it too, so nothing else in the project may build its own `ObjectMapper`.

## Design rules

- Follow SOLID. Aim for high cohesion and low coupling: each class/module has one reason to change, and dependencies point at abstractions, never at concrete implementations. The messaging rules above are an instance of this — services depend on `IPublisher`/`ISubscriber`, not on Kafka.
- Callers must be able to use an implementation entirely through its interface — never design so that a caller has to downcast to the concrete class. Any public method callers need, lifecycle included, belongs on the interface.
- If implementations hold resources that need releasing (connections, threads, clients), put the lifecycle on the interface: make it `extends AutoCloseable` and redeclare `void close();` (dropping the checked `throws Exception`) so callers get try-with-resources through the abstraction. See `IPublisher`/`ISubscriber` in `pollution-common` for the pattern.

## Testing rules

- Every module has unit tests under `src/test/java`, mirroring its main packages, run by `mvn test` (JUnit 5, declared once in the root pom for every module; surefire pinned there). A test exercises **one service alone**: the service's classes are built by hand, as its `Wiring` would build them, with fakes of everything the service talks to — never two services chained through a topic, real or fake, and never Kafka, Redis, Postgres, PurpleAir or Telegram. Not covered, by decision: the adapters over trusted libraries — `KafkaPublisher`/`KafkaSubscriber`, `RedisPollutionCache`, `PostgresPollutionRepository`, the Telegram HTTP call (only the message text it renders is tested), `JdkWebServer`/`JdkHealthServer`. Testing those means running the real thing behind them; that is integration testing, a separate decision.
- Shared test support ships as a **test-jar** of the module that owns the interface it fakes (`<type>test-jar</type>`, `<scope>test</scope>` in the dependents; Maven resolves it from the reactor, so a module-scoped run still needs `-am`), so every service uses the same fake and the fake sits next to its contract: `pollution-common` → `com.pollution.common.testing` — `MutableClock` (a `Clock` the test moves by hand), `RecordingPublisher<T>` (keeps every `send` with its key; can be told to fail), `ManualSubscriber<T>` (the test `deliver`s messages into the subscribed handler, on the test's own thread); `persistence-common` → `com.pollution.persistence.testing.InMemoryPollutionCache<T>` (an `IPollutionCache` in a map, behaving as the Redis one — JSON round-trip, TTLs against a `Clock`, Redis-style glob patterns; can be told to fail; `keys()` and `expiryOf()` let a store test assert its key layout and TTL). A fake only one service needs stays in that service's test tree — in a `testing` package when several test classes share it, next to the one test otherwise. No mocking library: the interfaces are small, and a hand-written fake says what it does.
- Tests never read `Config` or `Env`: every setting is passed in by the test. Thresholds are spelled out in the test (the alert service's `TestThresholds`) rather than loaded from `thresholds.json`; only `ThresholdsLoaderTest` reads the packaged file, to check that it is valid.
- Anything that depends on time takes a `Clock` (the collector service, the in-memory cooldown store, the cache fake) or a scheduler (the collector's two loops run on `ManualScheduler`, which runs a task only when the test calls `runAll()`); no test sleeps or waits.
- `pollution-common/src/test/resources/logback-test.xml`, shipped in that test-jar, is the tests' logging configuration on every module's test classpath (logback prefers it to `logback.xml`): console only, no `logs/` file, libraries at WARN. It is the one other logback configuration allowed.

## Logging rules

- All output in this project MUST go through the SLF4J logger — never use `System.out.println`, `System.err.println`, `printStackTrace()`, or `java.util.logging`.
- Always work with the actual SLF4J `Logger`, obtained via `PollutionLogger.getLogger(...)` from `pollution-common`.
- The logger variable must always be named `logger`:

  ```java
  private static final Logger logger = PollutionLogger.getLogger(MyClass.class);
  ```

- Use parameterized messages (`logger.info("wrote {} records", count)`), not string concatenation.
- Logback is the logging engine. The single shared `logback.xml` lives in `pollution-common/src/main/resources` and applies to all services via the classpath. Services must NOT add their own `logback.xml` — change the shared one instead. What it writes depends on `LOG_FORMAT`: `text` (the default) — the console in a human-readable pattern, and `logs/<service>.json` — one JSON object per line (logstash-logback-encoder; fields `timestamp`, `level`, `thread_name`, `logger_name`, `message`, `service` — the service name — plus `stack_trace` for a logged throwable; UNIX line endings), rolled daily with 7 days kept — which the observability stack reads; `json` — those JSON lines on stdout and no file, for a container platform that collects stdout (see *Running in containers*). `LOG_FORMAT` is the one variable read from the process environment by logback itself (its `<if>` needs the janino dependency of `pollution-common`), not through `Env`: logback configures itself while the first logger is created, before `Env` — whose own class initialization logs — can run; a `.env` file therefore cannot set it. `org.apache.kafka` is capped at WARN there: the clients narrate their whole configuration and every broker hiccup at INFO.
- The JSON file is named by the `app.name` system property. Every `*Application` sets it from `Config.SERVICE_NAME` by calling `PollutionLogger.initService(...)` in a static block placed ABOVE its logger field — static initializers run in textual order, and logback reads the property once, while configuring itself for the first logger; a `-Dapp.name` JVM flag from outside wins over the code's own. A new service's Application class must do the same, or its logs land in `logs/app.json` as service `app`.

## Running in containers

- Every application answers a container platform's probes through the `IHealthServer` interface from `com.pollution.common.health` (`pollution-common`): `GET /healthz` — liveness, 200 while the process runs — and `GET /readyz` — readiness, 200 from `markReady()` until `markNotReady()`, 503 otherwise. Ready means started (state restored, subscribed, listening), not that the stores behind the service are reachable. It listens on `HEALTH_PORT` (`com.pollution.common.config.Config.getHealthPort()`; unset or 0 — the default — means no server, so every service runs on one machine without choosing ports; a pod's manifest sets it), on every interface, since probes come to the pod's address, and on a port of its own in every service — the API service's too, not the dashboard's — so the health code exists once: `health/jdk/JdkHealthServer` over the JDK's `jdk.httpserver`, `NoopHealthServer` when the port is unset. Each `Wiring` has `createHealthServer()`. Each `*Application.main` starts it first, so liveness answers during a slow start (the analyzer's restore, the collector's enrichment), builds and starts its service, then marks it ready; a start that throws closes the health server before propagating, so the process ends instead of staying alive and never ready; the shutdown hook marks it not ready before closing anything and closes it last.
- Logs: `LOG_FORMAT=json` (see the logging rules; the Docker image sets it) — JSON lines on stdout, no file; the `service` field in every line replaces the file name Alloy labels by locally.
- Replicas: the analyzer and the alert service run as **one** instance each, by decision (to avoid work with no need behind it): their correctness relies on it — the analyzer's in-memory per-series state is loaded from the cache once at startup and would go stale when a partition moved between instances; the alert service's cooldown check-then-mark is atomic only within one JVM. Deploy them at one replica with a `Recreate` strategy, so an update never runs two. The writer and the API service can be replicated (the repository is idempotent, the latest-reading store never goes backwards) once the topics are created with more than one partition — every topic is auto-created with one today, so a second consumer instance would idle. The collector replicates by **membership**: one Deployment, any number of replicas, every one with the same `PURPLEAIR_SENSORS`; the instances find each other through Redis and share the sensors out by rank, so `kubectl scale` — or a pod dying — is followed by a reshare within a heartbeat or so, with nothing to edit. `COLLECTOR_ID` needs no setting: its default, `<hostname>-<pid>`, is the pod's name and the container's pid, the same again after a container restart. More replicas than sensors is allowed (the extra ones idle) but pointless. The collector needs Redis like the writer does; while Redis is unreachable a running instance keeps polling for one lease and then stops until it is back.
- The API service must bind to all interfaces in a container: `API_BIND_ADDRESS=0.0.0.0`.
- Shutdown: the hooks close the subscribers (each waits up to 5 s for its thread), the Telegram sender (a send may take up to `TELEGRAM_TIMEOUT_SECONDS`, default 10) and the stores; give a pod a termination grace period of about 30 s.
- Locally, a second collector: just start it — its id differs from the first one's by pid, and the two reshare the sensors within a heartbeat — and give it its own `-Dapp.name`, so its JSON log file does not collide with the first one's.

## Images and CI

- Every service jar is runnable: `mvn -DskipTests package` leaves `<service>/target/<service>.jar` (`finalName` is the artifact id, set once in the root pom) whose manifest names the application class and lists its dependencies as `lib/…` entries, next to `target/lib/` holding those dependencies — the root pom's `maven-dependency-plugin` execution `copy-runtime-dependencies` (`copy-dependencies`, runtime scope, at `prepare-package`). The five service poms opt in by declaring that plugin and the jar plugin's `mainClass`; a library module declares neither and stays a plain jar. `java -jar pollution-api-service/target/pollution-api-service.jar` runs a service from any working directory (`.env` is found upward from it, as always). Skip tests with `-DskipTests`, never `-Dmaven.test.skip`: the latter also skips compiling them, and with them the test-jars the reactor needs.
- One `Dockerfile`, at the repository root, builds every service: `docker build --build-arg SERVICE=<module> -t <module> .` (the daemon is WSL's, so build from there, with the `/mnt/c/…` path). Stage one packages the whole reactor with a cache mount for the Maven repository and uses no build argument, so it is identical for all five images and a layer cache serves it once. Stage two, on a JRE image, copies `target/lib/` and the chosen service's jar as two layers (a code change rebuilds only the small one), runs as an unprivileged user in `/app`, sets `LOG_FORMAT=json`, and starts `java -XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError -jar app.jar` — the heap follows the container's memory limit, and an out-of-memory error ends the process so the platform restarts it. Nothing else is set: `HEALTH_PORT`, the stores' addresses and the secrets come from the manifest that runs the container, and more JVM flags go in `JAVA_TOOL_OPTIONS`. `.dockerignore` keeps `.env*` (secrets), `target/`, `logs/`, `.git/`, `observability/` and the docs out of the build context; `.gitattributes` pins the Dockerfile to LF, since a CRLF line continuation breaks a build from the Windows checkout inside WSL.
- `.github/workflows/ci.yml`: on every push and pull request, job `test` runs `mvn -B -ntp verify` on Temurin 21 with the Maven cache (the surefire reports are uploaded when it fails), and job `chart`, alongside it, validates the Helm chart without a cluster: `helm lint --strict`, then `helm template` — with placeholder values for the two required secrets, since the `required` guard only checks that they are set and nothing rendered in CI is applied anywhere; once with the defaults and once with every optional value set, so the templates' conditional blocks render too — piped into kubeconform (a pinned release, downloaded in the job), which checks every rendered object against the Kubernetes OpenAPI schema of the version k3s runs, in strict mode, so a misspelled or misplaced field fails the run — the offline stand-in for the server dry run of the *Kubernetes* section; and a render missing either required secret must fail naming it. It cannot tell whether the pods come up; that stays with the WSL dry run. On a push to `main`, job `images` builds and pushes one image per service, a matrix of five, to GitHub Container Registry as `ghcr.io/yiftach128/<service>`, tagged `sha-<short commit>` (what a deployment names) and `latest`, authenticated with the workflow's own `GITHUB_TOKEN` (`packages: write`) — no secret to configure. The images are public, as the repository is. A newer push to the same branch cancels the run in progress. Actions are pinned to a major version.

## Kubernetes (k3s + Helm)

- The deployment is one Helm chart, `helm/air-pollution-tracker/` (`Chart.yaml`, `values.yaml`, `templates/`), written as plain Kubernetes YAML with a few `{{ .Values }}` substitutions — one template file per thing, no loop over the services — so each manifest reads on its own; `_helpers.tpl` holds only what every manifest repeats (the common labels, the two health probes, the config-checksum annotations). One release per namespace: resource names are fixed, not prefixed by the release name, so the stores answer to their plain names (`kafka`, `redis`, `postgres`) inside it. It targets the single-node k3s in the WSL Ubuntu distro (Traefik disabled there; ServiceLB, the `local-path` StorageClass and metrics-server on) and is operated only from inside that distro.
- What it deploys: a `Deployment` per service (`pollution-data-collector`, `pollution-data-writer`, `pollution-data-analyzer`, `pollution-alert-service`, `pollution-api-service`) from `ghcr.io/yiftach128/<service>:<image.tag>`, and the stores as plain Deployments too — `kafka` (one KRaft broker with the listeners spelled out and the Service name advertised, log on the PVC `kafka-data`, a fixed `CLUSTER_ID` so a re-created pod meets a volume formatted under the same id), `redis` (no volume — every key has a TTL) and `postgres` (database and user from the values, created on first start; data on the PVC `postgres-data`). Each store is one replica with a `Recreate` strategy. The two claims use the default StorageClass and carry `helm.sh/resource-policy: keep`, so `helm uninstall` leaves the data; delete the claim to start over.
- `Service`s (ClusterIP) exist only for the three stores and the API service; the other services expose nothing but their health port, which the kubelet probes at the pod IP. The dashboard leaves the cluster through `pollution-api-service`, type `LoadBalancer` by default (`apiService.service.type`): on k3s, ServiceLB takes `apiService.service.port` (8080) on the host, so the dashboard is `http://localhost:8080/` from inside the distro — and, from a Windows browser, `http://<EXTERNAL-IP>:8080/` with the address `kubectl -n air-pollution get svc pollution-api-service` shows (the WSL VM address, which can change when the VM restarts): ServiceLB claims the port with packet rules, not a listening socket, and WSL relays only listening sockets to the Windows `localhost`. `NodePort` is the alternative (a port from the 30000 range instead, same reachability).
- Configuration: the ConfigMap `pollution-config` (`KAFKA_HOST`, `REDIS_HOST`, `POSTGRES_HOST` — the Service names — `POSTGRES_DB`, `POSTGRES_USER`, `HEALTH_PORT`) goes to every service with `envFrom`; the API service adds `API_BIND_ADDRESS=0.0.0.0`. Every pod has `enableServiceLinks: false`: Kubernetes otherwise injects Docker-link variables for each Service in the namespace, and a Service named `kafka` would give every pod `KAFKA_PORT=tcp://<ip>:9092` — shadowing the numeric `KAFKA_PORT` the services read, likewise `REDIS_PORT` and `POSTGRES_PORT`. The secrets (`POSTGRES_PASSWORD`, `PURPLEAIR_API_KEYS`, and `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` only when set) form the Secret `pollution-secrets`, from which each pod takes only its own keys by name; they come from `helm/air-pollution-tracker/values-secrets.yaml` — git-ignored like `.env`, copied from `values-secrets.example.yaml`, passed with `-f` — and the two required ones fail the install with a message naming them when missing (`helm lint` does not enforce that; `helm template`/`install` do). A pod annotation carries the checksums of the ConfigMap and the Secret, so an upgrade that only changes configuration still rolls the pods.
- Replicas encode the decisions of *Running in containers*: the analyzer and the alert service are fixed at 1 with `Recreate` in their templates (no value to scale them by mistake); `collector.replicas` (default 2), `writer.replicas` and `apiService.replicas` (default 1: one partition per topic) are values. Every service pod has liveness `/healthz` and readiness `/readyz` on `healthPort` (8081), a 30 s termination grace period and memory requests/limits (the JVM heap follows the limit) with CPU requests only.
- Images: `image.tag` is one value for all five services, `latest` by default. A deploy of a known commit is `helm upgrade ... --set image.tag=sha-<short commit>`, which changes the pod templates and rolls them out; with `latest` nothing changes on upgrade and the pods need `kubectl rollout restart`. No pull policy is set: Kubernetes pulls `latest` on every start and any other tag once. The GHCR packages are public, so there is no pull secret.
- Install or upgrade, from a WSL shell in the repository: `helm upgrade --install air-pollution helm/air-pollution-tracker -n air-pollution --create-namespace -f helm/air-pollution-tracker/values-secrets.yaml`, then `kubectl -n air-pollution get pods -w`; logs with `kubectl -n air-pollution logs deployment/<service> -f` (the Docker observability stack tails files and does not see pods). A check that needs no secrets: `helm template air-pollution helm/air-pollution-tracker --set secrets.postgresPassword=x --set secrets.purpleAirApiKeys=x | kubectl apply --dry-run=server -f -`.

## Observability

- Logs are tracked in Grafana. `observability/` holds a Docker Compose stack — Loki (`3100`, 7-day retention, config in `observability/loki/`), Grafana Alloy (`12345`, config in `observability/alloy/config.alloy`) and Grafana (`3000`, anonymous admin, provisioned with the Loki datasource and the dashboards in `observability/grafana/dashboards/`) — run inside the same WSL-native Docker as Kafka/Redis/Postgres:
  `wsl -u root -e docker compose -f /mnt/c/Users/Yiftach/Documents/GitHub/air-pollution-tracker/observability/docker-compose.yml up -d`
- Alloy tails the repo's `logs/*.json` (mounted read-only; the daily-rolled `logs/*.<date>.json` files are excluded) by polling — the logs sit on a 9p mount where inotify never fires — and pushes each line to Loki with exactly two labels: `service` (from the file name; every line also carries it as a field, which is what a container platform's collector would use instead) and `level` (from the JSON). Labels must stay that bounded: anything else (logger, source, pollutant, …) is queried ad hoc with LogQL `| json`, never added as a label.
